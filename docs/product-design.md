## 1. 一句话定位

**观澜是 Mira Cloud 的基础新闻采集服务：接受用户的新闻源与关注点配置，持续采集轻量资讯索引，向 Mira 自有客户端中的 Agent/消费者提供稳定、统一、可追溯的结果视图，并分别记录每个消费者对每条新闻的处理状态。**

观澜是 **Mira Cloud Account 下的内建多用户服务**：账号创建时即注册观澜用户空间；Mira Desktop 与 Mira Mobile 共享账户中的配置和消费者状态。**首期及长期产品范围均不开放第三方 MCP 客户端接入。**观澜本身不依赖桌面开机，也**不是 Agent**。

目标是让 Agent 随时取到最新的候选新闻、按需自行 Web Fetch 原文、做完决定后明确写回状态，下一次即使换模型、换会话、换设备，也不会把已经完成处理的新闻误当成新任务。

## 2. 已确定的产品边界

### 2.1 必须提供

1. **公共源 + 两级私有订阅**：平台维护公共新闻源；每个 Cloud Account 有自己的订阅库与关注点，账户下每个消费者可继承账户配置并添加专属订阅/关注点。用户可添加 RSS、Atom 或支持发现 Feed 的网站地址。
2. **个人订阅私有**：个人订阅清单和关注点不进入公共目录，不被其他用户发现、推荐或查询。后台允许对同一个公共可抓取 URL 复用一次采集，但这种内部去重不得泄漏订阅者身份或隐私。
3. **账户与消费者关注点**：用户在账户层维护通用主题/关键词，消费者可额外配置自己的专属关注点；查询时按明确继承/合并规则形成有效视图。观澜只对标题、摘要和基础元数据机械过滤，不做 AI 语义匹配。
4. **非排他性查询**：默认可按关注点给出候选；授权 Agent 可以主动扩大查询到用户有权访问的来源与时间范围。未命中关键词不等于删除资讯。
5. **轻量采集**：保存标题、来源、摘要（以上游可用数据为准）、原文 URL、发布时间及必要元数据；不抓取、存储正文，不在云端生成 AI 摘要。
6. **严格去重**：只合并确认为同一原文 URL 的记录；可安全归一化已知追踪参数，但不能因为标题相近或事件相同就合并不同 URL。不同来源对同一篇文章的归属关联应保留。
7. **90 天新闻索引**：一般新闻记录保留 90 天，之后清理；为避免旧闻重新出现，必要的精简去重指纹和消费者处理记忆长期保留，仍受用户删除与数据治理要求约束。
8. **跨设备持久消费者身份**：消费者属于 Cloud Account，而非 Desktop/Mobile 设备或会话；同一消费者在不同设备及模型会话中共用一份身份与处理账本，不同消费者仍严格隔离。
9. **处理状态由消费者显式回写**：读取新闻本身无副作用。默认候选包含未读和已读待决，已采用和已忽略默认不返回，但可查询历史。最新候选优先，旧的待处理项保留、不阻塞新内容。
10. **决策附注可选**：采用或忽略时可以附理由、处理时间和成果链接；观澜只保存，不判断理由，也不负责发布或执行后续任务。
11. **账号创建即注册观澜**：Cloud Auth 创建 Mira Cloud Account 时，应同步触发可重试、幂等的观澜用户空间注册；旧账号须可补齐。观澜不建立独立账号或密码；Desktop/Mobile 已登录云账号即可无感取得受限的观澜服务凭证，不再出现一次登录/授权页面。消费者和工具仍各有权限边界。
12. **订阅变更仅可提议**：Agent 可以建议新增、移除来源或调整关注点；必须用户明确确认才生效，Agent 无权直接变更用户配置。
13. **双阅读格式**：同一份查询结果提供面向 Web Fetch 的 Markdown 视图和面向程序的 JSON 视图；**Markdown 优先、JSON 辅助**，不得独立维护两套数据。格式错误必须可检测，不能静默伪造结果。
14. **双鉴权入口**：支持携带标准授权凭证的接口，以及每消费者一条可撤销的**私人只读链接**；后者让普通 Web Fetch 也能读取，但绝不能凭链接写状态或管理配置。
15. **小时级刷新配置**：允许平台配置公共源间隔、用户配置个人源间隔；来源相同尽量复用抓取。具体允许的数值、配额、最低间隔仍需工程验证。

### 2.2 明确不做

- 不在观澜内置 Agent、LLM 推理、内容评价、写稿、推荐算法或自动研究工作流。
- 不在观澜里调用 Web Fetch 阅读全文；外部 Agent 可以拿到 URL 后自行阅读。
- 不做浏览器级通用爬虫，不默认抓网页正文，也不保证每个任意网站都能变成可采集来源。
- 不做语义软匹配、事件级聚类或因标题近似合并不同报道。
- 不让观澜替 Agent 决定是否采用、何时执行任务或成果去哪里发布。
- 不建立独立账号系统；不把 Cloud Auth 的统一身份与具体业务授权混为一谈；**不要求 Mira 用户为观澜二次登录、二次 OAuth 授权或手填 MCP Token**。
- 不做面向 Claude Desktop、ChatGPT 或其他第三方通用 MCP 客户端的接入、OAuth 客户端注册、授权页和外部应用生态；观澜的协议标准化不等于允许任意第三方消费。
- 不为了假想扩展，在首版引入专门的向量数据库、Agent 框架或第二套调度平台。

## 3. 数据归属与消费状态

### 3.1 逻辑实体（不是已冻结的数据库表）

| 概念 | 归属/用途 | 隐私与共享 |
| --- | --- | --- |
| Cloud Account | 统一用户主体，由 Cloud Auth 管理 | 账号创建即注册对应观澜用户空间；不复制密码/设备认证 |
| News Source | 可被抓取的原始来源及采集状态 | 相同 URL 后台可复用，不能反推出谁订阅 |
| Public Source Catalog | 平台公开提供的来源 | 可对全部获准用户展示 |
| Account Subscription | 账户级通用订阅、启用状态、刷新偏好 | 仅该账户可见；下属消费者可继承 |
| Account Interest | 账户通用主题、关键词等关注点 | 仅该账户可见；下属消费者可继承 |
| News Item | 规范化 URL、标题、摘要、发布时间、来源关系 | 按订阅/公共源权限返回，不因共享存储变成公开 |
| Consumer | 账户下稳定的消费身份（如 jianpi-radar） | 跨 Desktop/Mobile 共享，独立凭证/链接与处理账本 |
| Consumer Subscription / Interest | 消费者继承账户配置后的专属来源与主题增量 | 仅账户内获准管理者/所属消费者可见，不被其他消费者默认读取 | 
| Consumption Record | 某消费者对某条新闻的状态、原因、时间和成果链接 | 同用户其他消费者也不得被默认混用 |
| Subscription Proposal | Agent 提交的配置变更建议及用户审批结果 | 建议不会自动修改配置 |
| Fingerprint / Tombstone | 新闻过期后防重复的最少信息 | 不作为公开新闻历史目录 |

账户级订阅是消费者的**共享基础集合**；消费者可添加自己的专属订阅/关注点，不因继承而获得擅自修改账户基础集合的权限。继承/覆盖的精细规则及删除行为由实施合同确定，但不能让一个消费者的专属配置意外影响另一个。

这里的**底层采集共享**与**用户可见性**必须分开。一个私人订阅 URL 被两个用户订阅，并不意味着任一方能发现另一方、读取其配置或看到另一方的处理记录。

### 3.2 消费状态语义

| 状态 | 含义 | 默认候选 |
| --- | --- | --- |
| 未读（unread） | 尚无显式处理记录 | 是 |
| 已读待决（pending） | 已明确确认看过，尚无采用决定 | 是 |
| 已采用（adopted） | 消费者决定采用 | 否 |
| 已忽略（ignored） | 消费者决定不采用 | 否 |

- 记录键在概念上必须至少隔离 **用户 × 消费者 × 新闻**，不能用文章的全局状态代替。
- **GET / Web Fetch 不写状态**；显式确认或处理状态回写才改变账本。
- Agent 可以直接提交最终决定，不强制先标记 pending；写入应支持幂等重试。
- 一次取回 N 条不代表全部处理。任务崩溃后，未完成项继续留在候选池。
- 新一轮默认最新新闻优先，但允许分页取旧的 pending、历史 adopted/ignored。
- 新闻正文索引按 90 天清理后，仍保留最少的 URL 指纹与状态记忆，以免重复喂给同一个消费者；精简记录不能依赖已清理新闻的完整正文。
- 用户要求撤销凭证或删除个人数据时，必须有一致、可验证的撤销与删除路径；“长期保留”不代表永久不可删除。

## 4. Agent 消费契约

### 4.1 读与写彻底分开

**读取：** 按用户权限、消费者身份、关注点、来源、时间范围、状态、游标等条件查询；默认只返回该消费者尚未完成处理的新闻，最新优先。返回固定新闻 ID、标题、摘要、原文链接、来源、发布时间、状态及翻页信息。Markdown 与 JSON 来自同一次逻辑查询。

**主动探索：** Agent 可以放宽关注点条件，查看其有权访问的来源中的其他新闻；这是**取消过滤条件**，不是计算语义相关性。

**写回：** 通过受控且需授权的操作，按固定新闻 ID 标记 pending/adopted/ignored，可附理由与成果链接。必须返回明确的成功或失败响应；不能因为 Web Fetch 成功就认定状态已经写回。

**配置建议：** Agent 只能提交建议，等待用户批准或拒绝；授权读取新闻不赋予管理订阅权限。

### 4.2 人与 Agent 友好的结果

Markdown 作为低心智的默认阅读视图；JSON 作为受 Schema 约束的机器接口。下面是**展示格式示意，不是已经冻结的接口或真实资讯**：

~~~text
# Guanlan · jianpi-radar · 待处理
生成于：<ISO 时间>    后续游标：<opaque cursor>
过滤：关注点匹配；仅未完成；最新优先

## GL-10285 · 示例新闻标题
来源：Example Feed
发布时间：<ISO 时间>
状态：未读
摘要：由上游订阅源提供的简短说明。
原文：https://example.org/story/10285
~~~

~~~json
{
  "consumer": "jianpi-radar",
  "items": [
    {
      "id": "GL-10285",
      "title": "示例新闻标题",
      "summary": "由上游订阅源提供的简短说明。",
      "url": "https://example.org/story/10285",
      "source": "Example Feed",
      "publishedAt": null,
      "status": "unread"
    }
  ],
  "nextCursor": null
}
~~~

- 上述示例中的 ID、字段及 URL 都是**讨论接口形态的例子**，不是现有 API 路径、最终字段 Schema 或系统状态。
- 原文不由观澜读取。外部 Agent 按需使用自己的 Web Fetch；是否采用、为何采用由 Agent 决定。
- 结果须可分页、可追溯；失败时应显式返回错误，而不是混入假新闻或空结果掩盖服务故障。

### 4.3 标准 MCP 是 Mira Agent 的统一工具协议，不是第三方开放入口

[GLN-004](https://github.com/uichat-mira/cloud-guanlan/issues/8) 已交付受保护的 MCP Streamable HTTP 资源服务端。**MCP 是技术协议，Mira 自有 Desktop/Mobile 是唯一产品客户端**。观澜不运行 Agent、不提供第三方客户端注册，也不向最终用户展示通用 MCP OAuth 授权流程。

- 既有实现使用 MCP \`2026-07-28\` 无状态模式与官方 SDK v2，兼容 \`2025-06-18\`/\`2025-11-25\` legacy。服务端的 RFC 9728 metadata/401 挑战是已存在的底层协议能力，**不构成建设第三方 OAuth 生态或二次登录页的产品要求**；不得为实现产品目标删除或绕开现有安全检查。
- Desktop 和 Mobile 的自有云账号客户端根据 Cloud Auth 的有效 Cloud Session **无感换取观澜专用短期凭证**；每次 MCP 请求仍验证 audience、scope、账户与稳定 consumer，不直接把 Cloud Session 当 MCP Token，不把终端凭证硬编码进客户端。
- Desktop 由既有 Harness/Policy/Evidence 管理工具发现、启用及调用许可；Mobile 的 Local Provider Agent 通过自己的客户端工具边界执行，Remote Host 则由 Host 执行，**不跨设备共享凭证或审批权威**。
- 同一消费者身份可以从两个设备访问相同新闻与消费账本；不同消费者即便属于同一账户，也不能相互冒用身份。
- MCP 工具的读写 Schema、错误映射和权限语义保持单一真相源。用于 Desktop/Mobile 完整配置界面的管理 API 可以存在，但必须复用同一个领域服务和授权语义，不另造平行的 Agent API。
- **当前尚未交付：** 观澜用户空间注册、Cloud Auth 专用凭证签发、实际 Desktop/Mobile 客户端接线及真实账号 E2E；不要把 GLN-004 的协议代码当成这些能力已经上线。详见 [GLN-004 工程边界](engineering/gln-004-mcp.md)。

## 5. 身份、授权与安全边界（2026-11-01 维护者确认）

**账号体系**：Mira Cloud Account 是唯一终端用户主体，由 Cloud Auth 管理。Cloud Auth 创建账号的业务完成流程需要触发**观澜用户空间注册**；失败时有可观测的补偿/重试，且注册幂等。现有账号需要安全、可重复的补齐路径。具体使用事件、可靠任务或事务协调属于跨仓库技术设计，不把双数据库事务或“仅首次访问时懒创建”未经论证地写成产品事实。

**内部无感服务授权**：Desktop/Mobile 已登录 Mira Cloud Account 即可使用观澜，不需要再登录、单独开通、弹出观澜 OAuth 同意页或手动粘贴 Token。Cloud Auth 负责通过已有登录态签发**观澜专用、短期、可撤销**的凭证，携带被服务端认可的账户及稳定消费者身份；现有 Shiyan/Relay service token 和设备 Cloud Session 都不能直接当观澜工具凭证。无二次交互 **不等于**无服务器鉴权、无工具执行策略。

**跨设备消费者**：消费者是 Cloud Account 下的持久业务身份，既不等于云设备，也不等于一次 Agent 会话。同一消费者在 Desktop/Mobile 上恢复相同消费进度，消费者对订阅与处理状态的权限必须由服务端验证；不同消费者的状态/专属关注点默认不互相泄漏。消费者创建、选择、撤销与设备切换的 UI 将由两端提供。

**两级配置**：账户订阅/关注点对本账户消费者提供共享基础集合；每个消费者能在其上拥有专属来源与关注点。公共来源的后台抓取复用不意味着账户/消费者配置公开。订阅修改与建议批准仍是**用户管理操作**：Agent 只能提议，MCP 读取身份无权直接修改配置。

**MCP 与管理界面**：MCP 是 Mira Agent 的工具入口；Desktop/Mobile 都必须提供完整的新闻源、关注点、消费者管理能力。配置界面复用观澜唯一领域合同；不能通过另一个客户端维护与云端冲突的权威状态。Remote Host 与 Mobile Local Provider 路径各自遵守其执行及凭据边界。

**无第三方产品接入**：长期不承诺对 Claude Desktop、ChatGPT 或其他通用第三方 MCP 客户端开放 OAuth 注册、外部授权页或独立接入支持。GLN-004 已实现的 RFC 9728 资源发现保留为现有协议组件，但不再成为首期 OAuth 授权产品里程碑。若未来改变这一产品边界，须由维护者另行批准。

**Web Fetch 只读链接**：此前规划的每消费者高熵、可撤销私人 Markdown 只读链接是 Mira 自有 Agent 的辅助读取能力，不是面向第三方的开放集成。链接不能写消费状态或订阅；须防索引、跨用户缓存、Referer 泄漏、重定向外传，用户可轮换/撤销。若实现时发现此能力会引入没有产品收益的额外公网攻击面，应重新评估而非默认扩张。

**安全底线**：跨账户、跨消费者、scope 缺失、过期与撤销均须拒绝；不信任模型提供的身份名称。外部 Feed URL 的重定向、DNS/IP、SSRF、体积、超时风险须由服务端控制。对撤销与数据删除保留可验证的路径。

## 6. 采集、去重、刷新与保存

1. 以 RSS/Atom 和明确的公开资讯接口为首要输入，不默认支持任意 HTML 全文抓取。网站地址可尝试发现显式声明的 Feed。
2. 每个来源记录最后成功抓取时间、失败原因和下次到期时间；失败不能伪装为成功，也不能删除旧的已采集结果。
3. 支持**按小时为单位的采集间隔配置**。共享源的抓取频率如何合并多个用户偏好、最小可配置间隔和源数量上限，属于后续工程方案。
4. 同一篇文章按**可证实的规范化原文 URL**严格去重；不对同事件不同文章进行合并。归一化不得随意剔除所有查询参数，以免把不同文章误并。
5. 一份采集内容可以对应多个来源和订阅关系；删除一个人的订阅不能误删其他用户仍有权使用的共享数据。
6. 90 天后清理正常新闻索引；指纹和消费者决策保留精简数据。90 天的具体起算时间、重复入库时是否延长、过期后状态查询的展示形式，待技术设计定义并测试。
7. 尊重上游来源的速率、失败响应与使用条款，保留来源和原文链接；没有上游摘要时如实为空，不擅自抓全文补齐。

## 7. 低成本云架构：候选方案，不是已批准的技术合同

首选 **一个 Cloudflare Workers Free 服务 + Cron Trigger + D1**：

~~~text
Mira Cloud Account / 授权消费者
                |
       观澜 Worker（MCP + 管理 API）
          /           \
   账户/消费者配置与读写      定时采集入口（Cron）
          \           /
               D1
      来源 / 账户订阅 / 消费者专属配置
      新闻索引 / 消费状态
~~~

候选实现原则：

- 先验证 Worker + D1 能承载来源抓取、RSS/Atom 解析、定时任务及增量写入；**不要把 Node/Fastify/better-sqlite3 原封不动部署到 Worker**。
- 一个固定 Cron 每小时检查到期来源，按有界批次调度；不要为每条订阅创建 Cron。
- 普通读取只读数据库，绝不在 GET 请求中顺便抓网络或批量写入。
- 索引与过滤优先考虑 D1 的普通索引/明确查询；是否需要 FTS5 依真实规模验证，不把关键词筛选升级为向量检索。
- 采用去重后只写发生变化的记录、按批次抓取、限制来源/用户配额、观测 D1 row reads/writes 和 Worker CPU，而非一开始引入多服务架构。
- 账户级免费额度与其他 Mira 服务可能共享，不能把官方额度当成观澜独占预算。
- 设计目标是零额外费用，不承诺无限用户、无限来源、严格实时性或自动无感突破免费上限。

**2026-10-31 核查的 Cloudflare 官方参考（实施前重新确认）：**

- [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)：Free 每日 100,000 请求、单次 HTTP/Cron 执行 CPU 时间 10 ms、每次 50 个 subrequests、账户最多 5 个 Cron Triggers。
- [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)：Free 每日 5,000,000 行读取、100,000 行写入、账户总存储 5 GB；索引及查询扫描也会消耗额度。
- [D1 Free limits enforcement](https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/)：超日限额后查询会失败，不可假定可以透支。
- [Queues Free plan](https://developers.cloudflare.com/changelog/post/2026-02-04-queues-free-plan/)：以后可评估队列，但首版**不因为免费就默认引入**。

上述数字是**平台配额，不是本项目实测吞吐量**；解析复杂 Feed、用户鉴权、多人订阅并发和清理任务必须用真实 Worker 运行证据验证可行性。

### 7.1 部署形态选择（2026-11-01 维护者决定）

**首选 Cloudflare Workers，但不排斥阿里云。** Workers + Cron + D1 的低运维、低额外成本和按需调度优势仍符合观澜当前规模。**阿里云是经测试可考虑的备选承载形态，不是这次立刻迁移或部署双活的决定。** 服务形态要服从实际业务可达性、数据安全、维护成本和性能，而非为坚持某家平台反复消耗工程投入。

维护者特别强调：**中国大陆网络环境下的实际可达性是重要决策变量**，不能仅凭全球可访问或某地成功一次，就认定中国大陆访问稳定。将来选择 Worker、阿里云或区域部署前，需要分别从实际目标网络验证：

- **入口可达性：** Mira Mobile/Desktop、Agent 客户端能否稳定访问观澜域名/API；按网络运营商、DNS/TLS、HTTP 响应、丢包/超时和持续时间记录，不拿 VPN 下成功代替大陆直连。
- **出口可达性：** 采集运行地能否稳定访问需要的 RSS/Atom 来源；部署在国内阿里云并不自动意味着能够访问全部境外新闻源，可能反而需要适配网络与上游限制。
- **数据层可迁移性：** 当前 POC D1 具有特定 API 与事务/租约语义；如果选择阿里云，须设计可验证的持久化替换、备份/迁移和权限边界，不能假定将 Worker 代码原样运行即可。
- **实际成本：** 若采用已有阿里云实例，应核对剩余 CPU/内存、带宽/流量、运维、备案与访问风险；云上备用并不自动等于零费用。

**当前不建设额外 Worker 分流、跨区域负载均衡或 Worker + 阿里云双活。** 未来是否拆分采集与查询、增加第二个 Worker，依据真实来源规模、CPU 尖峰、请求/免费配额及客户端可达性决定，并先验证收益。Cloudflare Free 的单次 Cron CPU 上限是每次调用的约束，**单纯增加一个相同 Worker 并不能让原来的单次调用获得更多 CPU**；只有实质上拆开有界工作及各次调用，才可能降低单次处理负担，且还要检查共享的账户级配额、调度与数据库协调成本。<https://developers.cloudflare.com/workers/platform/limits/>

**近期实施优先级**：先完成单 Worker 采集链路的解析 CPU 优化及真实 D1/Free 实测，保留经验证的租约/去重；随后根据业务价值实现来源、授权消费和状态闭环。除非中国大陆实测出现明显阻断或本地成本不可接受，不为“可能被墙”提前开发双部署与智能路由。

### 7.2 GLN-003 当前研究结论与可信度（非上线验收）

截至 2026-10-31 UTC，**仅专属隔离 Cloudflare Canary** 已证明真实 Worker、Cron、RSS/Atom 拉取、D1 原子领取/过期租约围栏、事务写入、失败退避和 URL 去重可工作。Canary 不是生产环境，不存在正式云账号订阅或公开新闻读取/状态回写 API。

- 25 条 Atom 首次入库：原始逐条 SQL 单次观察 **32ms CPU**，改为 JSON1 批量写入后同源单次观察 **26ms**；不同时间独立调用，不能推断稳定提速百分比。
- 针对同一公开 Atom（25 条、约 32,218 字符），Cloudflare 的 9 次真实 scheduled 三阶段实验：仅拉取 CPU **4/4/6ms（中位 4）**；拉取 + XML 解析/字段归一化 **14/13/31ms（中位 14）**；完整采集含 D1 **18/45/19ms（中位 19）**。完整模式附加测试 SQL，且一次首次写入、两次 URL 去重，不能直接用阶段差当作精确的模块 CPU。
- **工程判断：解析环节是确定性高增量，D1 完整路径存在高值波动；尚未定位到具体函数的排他性热点。** Free 的 Cron 10ms CPU 上限目前缺乏可靠余量，偶发 26/32/45ms 成功不代表可以长期依赖豁免；不能外推 P95/P99、容量或免费持续稳定性。
- 验证结束，临时诊断表已清除、正式应用 bundle 已恢复、**Canary Cron 已停用**。保留隔离 Worker/D1 便于后续受控验证，原有 Mira 其他服务不受影响。
- 研究证据唯一详表：[GLN-003 Cloudflare CPU 三阶段实测](engineering/gln-003-cpu-profile.md)；[GLN-003 隔离部署/容量记录](engineering/gln-003-cloudflare-canary.md)；[Issue #6](https://github.com/uichat-mira/cloud-guanlan/issues/6)。这里只记录产品部署策略和有条件的工程结论，后续新样本统一写回工程报告。

## 8. 与 Desktop/Mobile 及现有本地观澜的关系

Desktop [mira-desktop/dev](https://github.com/uichat-mira/mira-desktop/tree/dev) 已有本地 NewsHub（来源、RSS/Atom、SQLite 缓存、检索适配与界面）。云观澜的账户配置/消费者账本是独立的云端权威，**本设计未授权删除或重写本地 NewsHub**；共存、迁移和离线缓存须在检查真实代码后签订明确合同。

- **Desktop**：云账号登录后无感连接观澜，Agent 通过现有 Harness/Policy/Evidence 执行工具；同时提供**完整**的新闻源、账户关注点、消费者及消费者专属配置管理界面，而非只有一个 MCP 连接按钮。
- **Mobile**：同样提供**完整**的管理能力；Local Provider Agent 可以直接以本设备云账号身份调用观澜 MCP，**不依赖 Desktop 在线**。Remote Host 模式继续由 Host Harness 执行，不能把 Host 凭证分发给手机或让手机假装 Host 工具已经执行。
- **跨设备**：同一 Cloud Account 的同一消费者选择后使用同一个云端处理账本。各端界面可以采用各自平台适宜的布局，但功能范围不得缩减为“仅查看新闻”。
- **Cloud Auth**：拥有账号创建与用户空间注册的触发合同、服务凭证签发/撤销；观澜拥有用户空间和新闻配置数据，不能复制 Cloud Auth 的账号认证数据库。
- **第三方**：不做通用 MCP OAuth 外部接入；现有协议元数据与 legacy 兼容保留，不用它们反推出开放生态需求。

以上是经维护者确认的目标，不代表 Desktop/Mobile/Cloud Auth 已经实现这些能力。

## 9. 端到端验收故事（后续工程合同的输入）

1. 新建 Mira Cloud Account 时自动、幂等注册观澜用户空间；旧账号可补齐，失败可重试且不能静默丢失。两个用户订阅同一公共 Feed 时后台复用抓取，但彼此看不到私人配置。
2. 同一账户的 jianpi-radar 和 qishu-research 继承账户公共订阅并分别添加自己的来源/关注点，读取同一新闻时前者忽略、后者采用，二者历史互不覆盖。
3. Desktop 上的同一消费者读取 30 条、处理 12 条后进程退出；在 Mobile 上选择同一消费者时已完成的 12 条不再作为待办返回，剩余项目可继续处理，不要求设备在线同时连接。
4. Agent 放宽关注点过滤后，可以看到本来未命中的、仍有权限的新闻，不需要运行语义模型。
5. 同一 URL 由多个来源提供时仍是同一新闻，而不同 URL 即使标题近似也不能误合并。
6. 新闻到期清理后，如果来源重新提供旧 URL，仍能通过指纹和账本避免对已完成消费者重复发新任务。
7. 只读私有链接可以被 Web Fetch 读取，但无法写状态；撤销该链接后再次读取应拒绝。
8. Agent 提交订阅变更建议后，账户或消费者配置保持不变，直到用户在 Desktop 或 Mobile 明确批准；两端均可完整管理来源、关注点及消费者。
9. 外部来源超时、Feed 非法、Cloud Auth 不可达、D1 达到限额时，系统显示真实失败而不是将空白当作“没有新闻”。
10. 在真实 Workers Free 限额下验证小时级调度、采集 CPU、D1 读写、身份隔离、缓存策略和恢复方式，不能把单元测试当成上线验收。

## 10. 待决事项——不得默认替维护者拍板

### 产品尚未拍板

- **免费额度逼近上限时的优先级**：优先保证新闻读取和状态回写、优先采集，还是公平降频？上一轮讨论提出了选项，**用户尚未选择**。不得把“优先读”写成已经确定的策略。

### 工程应测量和定案（无需反复请用户回答低价值细节）

- 源数量、每用户订阅数量、并发上限、调度批次与每小时间隔的具体范围。
- 共享同源时怎样合并用户不同的采集周期，以及来源失败退避和限流。
- 90 天期限起点、长期指纹/状态精简策略、删除与数据迁移。
- URL 归一化规则、订阅源解析边界、Feed 重定向和 SSRF 防护。
- 消费者凭证格式、Cloud Auth audience/scope 对接、撤销生效时间及只读链接的泄露保护。
- API 路径、分页游标、Markdown/JSON Schema、状态写回冲突与幂等契约。
- 从桌面本地 NewsHub 到云端的过渡和是否保留离线缓存。
- Cloudflare Free 实际可行性；若实测无法满足核心产品需求，再提交清晰的成本与取舍建议，不擅自升级付费。

| B4 | \`mira-desktop\` | **完整桌面管理 UI**：公开源与自定义来源、账户订阅库、账户/消费者关注点、消费者创建/选择/撤销及状态/错误反馈，不止 MCP 连接入口。 |
| B5 | \`mira-mobile\` | **完整移动管理 UI**：同等新闻源、账户订阅库、关注点、消费者及授权管理能力；交互适配移动端，不复制桌面布局或服务端状态机。 |
| B6 | \`cloud-guanlan\` | Mira 自有消费者按需使用的可撤销只读 Markdown Web Fetch 链接；不得写状态/订阅，不向第三方推广或绕过内部账号权限。必要性与泄漏面在立项时再次判断。 |

**B 出口：** Desktop 和 Mobile 均能**真正管理**账户/消费者新闻配置；同一消费者跨设备接续；从不要求再次注册或登录观澜。

### 12.3 C 阶段：用户决策与生产运行（3 个候选包）

### 12.4 跨仓库依赖、约束与本次取消的工作

- **优先依赖**：A2 用户空间注册、A3 内部服务凭证是并行可拆的合同；A4 必须基于它们共同的稳定账户/消费者身份。A5/A6 提供业务闭环，A7 使 Desktop 真正调用，A8 以真实运行链路验收。B4/B5 依赖 B2 统一管理合同，B3 使用 A3/A4/A6 共享的消费者身份。
- **取消旧 A3**：不再建设“标准 MCP OAuth 客户端发现、注册、第三方授权及 token 获取页面”作为用户交付目标。GLN-004 已有的资源发现/401 标准行为保留，不拆除现有安全边界；若要实现单纯内部 token 交换，只归 A3 内部服务凭证任务，**不扩展到第三方授权产品**。
- **权限不降级**：免二次授权仅指 Mira Cloud 已登录用户**不需要再次交互授予观澜服务资格**；每个消费者的资源访问仍受服务端认证鉴权，Desktop 工具执行仍走现有 Harness，Mobile Local/Remote 各守自身权限边界。
- **账号创建链路**：用户选择的是注册时自动拥有空间，不能悄悄降成纯首次调用懒创建；但可靠的跨服务调用/异步补偿与旧账号回填需工程设计和可观测证据，不假定跨 Cloud Auth/Cloudflare 数据库存在分布式原子事务。
- **部署限制**：GLN-004 只入 \`dev\`，当前尚未联通真实 Cloud Auth、两端 UI 或生产。Workers Free 10ms Cron CPU 仍无充足余量，中国大陆可达性仍要实测；不为了规划而提前多活/开通付费。
- **执行管理**：GitHub Issue 是任务契约的唯一真相源，本文不维护实施状态台账、不制造已存在的 17 张任务卡；正式派卡前按现行组织 Skill 确认归属、依赖与验收。

**当前已完成的独立合同入口：** [GLN-004](https://github.com/uichat-mira/cloud-guanlan/issues/8)。剩余部分按依赖逐批建正式任务卡；这份规划不自动授权开工或部署。
